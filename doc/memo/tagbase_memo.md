# タグベースのメモ帳の設計

https://github.com/mitoma/kashiki2/issues/80

現在のメモ帳は 1 つの JSON ファイルで管理されており、カテゴリごとにメモ本文の配列を持つ。

```json
{
    "current_category": "default",
    "categorized": {
        "category_name": {
            "memos": [
                "メモの内容",
                "別のメモの内容"
            ]
        }
    }
}
```

しかし、このようなメモ管理には以下の問題があった。

- カテゴリごとにメモが固定されてしまい複数のカテゴリにまたがるメモを管理しづらい
- 検索性が低く、目的のメモを見つけにくい
- 作成日時、更新日時といった時系列に沿った管理がしづらい
- 一つの JSON ファイルに全てのメモが詰め込まれてしまい部分的なファイルの活用がしづらい

これらの問題を解決するために、タグベースのメモ管理を導入する。

## 要求

- メモの作成当初は日時の情報のみがあればよい
- タイトルやタグは後からつけたい
- 複数のタグを加えたい
- 無題メモを多数書きたい（scratch 的なメモにはタイトルを付けることも考えたくない）
- タグに関係なく時系列で眺められるようにしたい（emacs change-log の使い勝手が必要）
- 文字列を入力することで横断検索でメモを見つけられるようにしたい

## 設計案

### ディレクトリと設定の責務

あるディレクトリをメモ保管庫のルートとして設定し、そのディレクトリ内のファイルレイアウトに従って管理する。

```text
.gitignore
kashikishi-state.toml
kashikishi-tagbase-settings.toml
memos/
  2026-06/
    2026-06-18-001.md
    2026-06-18-002.md
    2026-06-18-003.md
    2026-06-19-001.md
  2026-07/
    2026-07-01-001.md
    2026-07-02-001.md
```

`kashikishi-tagbase-settings.toml` には保管庫で共有する設定情報を持たせる。

```toml
tag_definitions = ["scratch", "todo", "diary", "works", "archive"]
default_tag = "scratch"
invisible_tag = "archive"
```

`kashikishi-state.toml` にはユーザー個人の表示・編集状態を持たせる。
これは個人用の状態のため、他のユーザーと共有せず、`.gitignore` に含めてバージョン管理の対象外とする。

```toml
# narrowing_tag は絞り込みに使用するタグのリスト。
narrowing_tag = ["todo", "scratch"]
# sort_order は作成日時の昇順（"asc"）または降順（"desc"）を指定する。
sort_order = "desc"
```

このディレクトリ自体の履歴管理を Git などのバージョン管理システムで行うことでメモの変更履歴を追跡できるようにする。

- `TagbaseMemo::new(...)` に渡すパスをメモ保管庫のルートとし、その直下に設定ファイルと `memos/` を置く。
- 保管庫の設定はライブラリで扱い、ユーザー個人の表示・編集状態の保存・復元はライブラリ利用側の責任とする。
- `tag_definitions` はタグ入力時の候補であり、使用可能なタグの制約ではない。候補にないタグも使用できる。
- `default_tag` は、新規メモの作成時にのみ自動で付けるタグとする。作成後は削除でき、既存メモの読み込み・更新時には補わない。
- `invisible_tag` を持つメモは、通常の一覧・検索・タグ絞り込みから除外する。そのタグを絞り込み条件として明示的に指定した場合のみ表示対象にする。

### ファイル名と並び順

- ファイル名は `memos/YYYY-MM/YYYY-MM-DD-NNN.md` とする。日付は作成時のローカル日付、メタデータの日時はローカルの UTC オフセット付き RFC 3339 形式で記録する。
- `NNN` は同じ日の既存ファイルの最大値に 1 を足して採番する。削除などで欠番ができても詰め直さない。
- 作成後のファイル名は変更しない。ファイル名は保管上の識別子として扱い、作成日時の代わりにはしない。
- メモ ID は保管庫ルートからの相対パスとする。外部でファイル名が変更された場合は別の ID のメモとして扱い、元の ID との同一性は追跡しない。外部で削除された場合は、その ID のメモが存在しなくなったものとして扱う。
- 同名ファイルが存在する場合は、既存ファイルを上書きせず、再採番する。複数プロセスからの同時作成は対象外とし、炊紙の多重起動はないものとする。
- 一覧の既定順は作成日時の降順とし、同じ日時の場合はファイル名の昇順で安定して順序を決める。利用側は `sort_order` に応じて作成日時の昇順・降順を指定する。

### front matter とメモの更新

メモは YAML front matter と Markdown 本文で構成する。

```markdown
---
created_at: 2026-06-18T12:34:56+09:00
updated_at: 2026-06-18T12:34:56+09:00
title: メモのタイトル
tags: ["scratch", "todo"]
---

メモの本文
```

- front matter は YAML とし、`created_at` と `updated_at` はタイムゾーン付き RFC 3339 形式、`title` は省略可能な文字列、`tags` は文字列の配列とする。
- 無題のメモは `title` を省略し、タグがないメモは `tags: []` とする。本文が空でも有効なメモとして扱う。
- `created_at` は作成後に変更しない。本文・タイトル・タグのいずれかが変更された場合に `updated_at` を更新する。変更がない場合は更新しない。
- front matter を読めないファイルがあった場合、黙って無視せず、ファイルパスを含むエラーとして返す。
- 保存時は一時ファイルに書いてから置き換える方式を基本とし、書き込み途中の停止による破損を避ける。
- 外部更新との競合検出は初期実装の対象外とする。競合検出を実装する際の対応方針は「未決事項」に記載する。

### 検索とタグ絞り込み

- キーワード検索はタイトルと本文を対象とし、まずは大文字・小文字を区別しない部分一致とする。タグ検索はタグ絞り込みとして別の操作にする。
- タグ名の比較は完全一致とする。複数タグを指定した場合は、すべてのタグを持つメモに絞り込む（AND 条件）ことを暫定案とする。
- キーワード検索とタグ絞り込みを組み合わせるため、`キーワード tag:タグ名1 tag:タグ名2` 形式の簡単なクエリを用意する。`tag:` で指定した値は本文検索の対象ではなく、タグの絞り込み条件として扱う。キーワード条件とタグ条件の両方を満たすメモを返す。
- 検索 API に空クエリを渡した場合、またはタグ絞り込み API に空のタグリストを渡した場合は、`default_tag` を指定したタグ絞り込みとして扱う。この規則は空クエリに対するものであり、キーワードだけの検索に `default_tag` 条件を追加するものではない。タグに依存しない一覧取得は一覧取得 API を使用する。
- 空白を含む文字列や、キーワードとして検索したい `tag:` で始まる文字列は、二重引用符で囲む。引用符内は空白による分割や `tag:` による条件指定として解釈せず、一つの文字列として扱う。例えば、`"tag:example"` はタイトル・本文中の `tag:example` を検索する。
- `tag:` の後に引用符で囲んだ値を指定すると、その値全体をタグ名として扱う。例えば、`tag:"my tag"` は空白を含むタグ名 `my tag`、`tag:"tag:example"` はタグ名 `tag:example` で絞り込む。
- `invisible_tag` を持つメモは通常の検索・タグ絞り込みから除外する。ただし、クエリの `tag:` またはタグ絞り込み API で `invisible_tag` 自体を指定した場合は表示対象とし、ほかの検索・絞り込み条件も適用する。
- 検索・絞り込み結果も「ファイル名と並び順」と同じ規則で返す。
- 日本語の形態素解析や高度な全文検索は初期実装の対象外とし、必要になった場合に追加する。

### API とエラー

`tagbase_memo` クレートとしてライブラリ化し、以下の操作を提供する。

- メモの作成・更新・削除・検索・一覧取得はライブラリの API として提供する。時系列で眺める要件を満たすため、タグに依存しない一覧取得 API も用意する。
- ファイル操作や front matter の解析に失敗する可能性があるため、それらを行う API は読み取りも含めて `Result` を返す。
- 更新 API はメモ ID を受け取り、更新後の内容を永続化するところまでを行う。更新対象が見つからない場合はエラーとして返す。初期実装では外部更新との競合は検出せず、外部で編集された内容の上書き防止は保証しない。
- 削除は初期案ではファイルを削除する。Git 管理を利用する場合は Git の履歴から復元できるが、Git はライブラリの必須要件とせず、ライブラリ自身は Git コマンドを実行しない。

#### インターフェイスのイメージ

以下は API の利用イメージであり、型やシグネチャは実装時に確定する。`?` を使える、`Result` を返す呼び出し元を想定する。

```rust
let memo_repository = TagbaseMemo::new(".")?;

// メモの作成
let memo = memo_repository.create_memo()?;

// メモの編集
memo_repository.update_memo(&memo.id, |m| {
    m.title = Some("新しいタイトル".to_string());
    m.tags.push("todo".to_string());
})?;

// メモの検索
let search_results = memo_repository.search("キーワード")?;

// キーワードと複数タグで検索
let narrowed_results = memo_repository.search("キーワード tag:todo tag:scratch")?;

// 空白を含むタグ名で絞り込み
let spaced_tag_results = memo_repository.search(r#"tag:"my tag""#)?;

// tag: で始まる文字列をタイトル・本文から検索
let literal_results = memo_repository.search(r#""tag:example""#)?;

// tag: で始まるタグ名で絞り込み
let prefixed_tag_results = memo_repository.search(r#"tag:"tag:example""#)?;

// タグで絞り込み
let filtered_results = memo_repository.filter_by_tags(&["todo"])?;

// 空クエリ・空のタグリストはいずれも default_tag で絞り込む
let default_search_results = memo_repository.search("")?;
let default_tag_results = memo_repository.filter_by_tags(&[])?;

// 非表示タグを明示して検索
let archived_results = memo_repository.search("tag:archive")?;
```

### 既存メモからの移行

既存のカテゴリ別メモからの移行は、現段階では検討・実装の対象外とする。変換方法や移行用 API は今回の設計では定義しない。

### 初期実装の範囲

`tagbase_memo` クレートを作成するところからスタートする。
まずはファイル保管庫、メモの作成・更新・一覧・タグ絞り込み・キーワード検索を実装する。
GUI 上の編集状態の保存、外部更新との競合検出、複数プロセス間の高度な同期、全文検索インデックス、Git 操作、既存メモからの移行は初期実装の対象外とする。

### 未決事項

- **外部更新との競合検出**: 実装は後回しとし、競合を判定するための比較対象や、更新 API に渡す情報は未決事項として残す。将来の実装では、競合を検出した場合は保存せずにエラーを返し、呼び出し元で編集中の内容と外部更新された内容を確認して、Git のコンフリクト解消のように手動で解消してから再度更新する方針とする。ライブラリによる自動マージや強制上書きは行わない。
